# Задача

Определи id задачи из git: `git branch --show-current` (если пусто —
`git rev-parse --abbrev-ref HEAD`), из имени ветки извлеки id по паттерну `[a-z]+-\d+` (например
`compass-3951`). Если id не находится — спроси у пользователя.

# MR по текущей ветке

Попробуй найти MR через GitLab MCP (`gitlab`):

- `gitlab_list_merge_requests` с фильтром `source_branch = текущая ветка`, `state = opened|merged`,
  без `project_id` (по всем доступным проектам);
- из каждого MR возьми путь проекта и iid.

Если MCP `gitlab` недоступен или MR не найдены — спроси у пользователя ссылки на MR.

# Нормализация

Каждую ссылку MR приведи к виду `.../-/merge_requests/<iid>/diffs` — чтобы открывался сразу дифф.

# Источники саммари

- Коммиты ветки: базу найди через `git log --no-merges ... origin/master..HEAD` (если такой ветки нет —
  `origin/main`, `master`, `main`), затем `git log --no-merges --format='%s%n%b' <base>..HEAD`.
- `.opencode/work/<ветка>/task.md` и `task-log.md`, если существуют.
- Текст из `$ARGUMENTS` — подсказки пользователя, учти их в саммари.

В diff и код не лезь: нужно понять, что сделано, а не как.

# Правила саммари

- 2–6 пунктов простым списком `- `. Никаких заголовков, жирного, курсива, таблиц, блоков кода,
  вложенных списков и эмодзи.
- Пиши на языке задачи и бизнеса, а не кода. Не упоминай имена классов, методов, файлов, таблиц,
  переменных, SQL, конфиги, библиотеки, хеши коммитов.
- Каждый пункт — одно короткое предложение в прошедшем времени: «Добавлена выгрузка…»,
  «Исправлена ошибка при…».
- Если что-то не сделано или отложено — допустим один пункт «Не вошло: …».
- Ничего не выдумывай: только то, что подтверждают коммиты и task-файлы. Мало источников —
  пиши коротко, не раздувай.

# Формат комментария

Сначала MR, затем саммари; группы разделяются строкой `___`:

```
HUB-SDK-LIB: <link>
___
SDK1: <link>
SDK2: <link>
___
SERVICE1: <link>
SERVICE2: <link>
___
Что сделано:
- ...
- ...
```

Группировка MR: проекты SDK первыми, затем остальные сервисы. Внутри группы — исходный порядок.
Писать с `usesMarkdown: true` (нужно для `___` и списка; другой разметки не добавляй).

# Черновик

Прежде чем писать в YouTrack, покажи пользователю полный текст комментария и дождись
подтверждения или правок.

# Куда писать

Получи комментарии задачи (`youtrack_issue_comments`):

- есть свой комментарий и он последний в списке → обнови через `youtrack_issue_comment_update`:
  блок «Что сделано» замени новым саммари, списки MR объедини (добавь новые, удали дубликаты по
  iid, сохрани порядок SDK → сервисы);
- свой комментарий есть, но не последний → создай новый через `youtrack_issue_comment_create`, но
  сначала спроси пользователя: перенести весь список MR в новый комментарий или добавить только
  новые MR;
- своего комментария нет → создай новый.

# Поле MR Gitlab

После записи комментария заполни поле задачи «MR Gitlab» основным MR:

1. Основной MR: если MR один — он; если несколько — спроси пользователя, какой основной, показав
   список MR.
2. Значение — та же нормализованная ссылка `.../-/merge_requests/<iid>/diffs`.
3. Текущее значение возьми из `youtrack_get_issue` (`fields["MR Gitlab"]`):
   - пусто → записывай;
   - та же ссылка → ничего не делай;
   - другая ссылка → спроси пользователя, перезаписывать ли.
4. Запиши через `youtrack_set_mr_field`. Если в проекте нет такого поля — сообщи об этом, но не
   считай это провалом команды.

# Проверка

После записи перечитай `youtrack_issue_comments` и подтверди, что комментарий на месте, ссылки
корректны, а в саммари нет кода и имён файлов. Перечитай `youtrack_get_issue` и подтверди, что в
поле «MR Gitlab» нужная ссылка.
